01THE PROBLEM

相同的 Prompt 前缀，为什么要重复算一遍？

LLM 推理天然分成 Prefill 与 Decode 两段：Prefill 决定 TTFT（首 Token 时延），Decode 决定 TBT（Token 间隔）。而在真实业务里，往往有大量请求共享同一段前缀——系统提示词、多轮对话历史、Agent 的工具指令模板。传统部署中，KV Cache 跟着实例走，跨节点之间互不可见，同样的前缀被反复计算。

三种主流 Prefix Caching 方案

方案代表框架核心技术缓存粒度特点与适用场景
RadixAttentionSGLang基数树（Radix Tree）管理 KV Cache，支持最长前缀匹配Token 级，前缀匹配灵活共享前缀（System Prompt / 多轮历史）复用率高，显著降低计算量；适合多轮对话、Agent、Few-shot
Automatic Prefix CachingvLLM基于哈希的块级缓存KV 块级，只缓存完整块实现简单、框架内集成，有成熟缓存隔离（Salting）安全机制；适合通用与多租户隔离场景
MooncakeMooncake（vLLM 集成）分布式 KV Cache 池，把 Cache 卸载到 CPU、SSD 等共享存储块级，跨实例共享扩展范围把 Prefix Caching 从单机扩展到分布式集群，多实例共享缓存，极大提升有效承载；适合大规模分布式部署
CORE IDEA 将计算过、可能被共享的 prompt 前缀 KV Cache 持久化到公共池；新请求通过最长匹配复用已有缓存， 仅对增量部分计算。同一前缀“只算一次、只存一份”，这就是 Prefix Caching 的本质。
02ARCHITECTURE

以 KV Cache 为中心的 KVCache-centric 解耦架构

传统推理中，KV Cache 是 GPU 实例的附属状态。Mooncake 把 Prefill 与 Decoding 部署到不同资源池，再把集群里闲置的 CPU、DRAM、SSD 组织成分布式 KV Cache 池——KV Cache 成为独立于计算实例、可共享调度的资源。全局调度（Conductor）与局部调度（实例调度器）协同优化。

把“用了 Mooncake”拆成四层看

分层主要职责Mooncake 中的对应能力
调度与编排层集群部署、扩缩容、请求路由、缓存位置感知、PD 资源调度Conductor / 缓存感知调度思想；开源生态中也可由外部 Router 承担
推理执行层模型计算、Continuous Batching、Attention、并行、投机解码Mooncake 不替代推理引擎，可接 vLLM、SGLang 等
KV Cache 存储层GPU 外缓存扩展、索引、淘汰、跨节点复用、生命周期管理Mooncake Store
数据传输层PD 间 KV 传输、跨节点数据移动、RDMA / GDR 等Mooncake Transfer Engine
口径提醒 “某系统使用 Mooncake”至少要继续说明是哪一层：只用 Transfer Engine 做高速数据移动； 用 Mooncake Store 建分布式 KV Cache 池；还是同时采用缓存感知调度、PD 编排与全局 KV 管理的完整架构。 这三者的工程量与收益完全不同。

03REQUEST LIFECYCLE

一次请求，四段链路

Prefill 与 Decode 被拆到不同实例后，KV Cache 必须在两侧之间“搬家”。Mooncake 用KVCache Reuse → Incremental Prefill → KVCache Transfer → Decoding四步完成闭环，其中第三段由 Transfer Engine 承担，并与 Prefill 计算重叠执行。

四段链路的工程细节

STEP 01 KVCache 复用

Conductor 选定合适的 Prefill 节点 / 组；请求携带 raw input、可复用的 prefix block IDs 与完整请求所需 block IDs。Prefill 节点按 prefix block ID 把 CPU 中的 KV 载入 NPU，作为计算初始状态；无可用前缀则跳过。

STEP 02 增量 Prefill

只计算未缓存部分，完成后把新 KV 存回 CPU。未缓存 token 超过阈值（prefill_chunk，通常 >1000 tokens）时走流水线：分块执行，使 Prefill 计算与 KV 传输并行，提高吞吐。

STEP 03 KVCache 传输

Messenger 运行在独立推理进程中，异步管理跨机 KV 传输（GPUDirect RDMA / HCCS）。计算增量 KV 的同时传输已算好的部分，避免“等全部层算完才传”的尾部等待。

STEP 04 Decoding

所有 KV 到达解码节点 CPU 后，请求加入连续批处理队列。Conductor 依据当前负载预选解码节点以保证 TBT SLO；本地调度器会二次检查，若预期变化可能拒绝请求——此时前面的 Prefill 成本会被浪费。

块级哈希：前缀匹配到底在匹配什么

WHY CHUNKED 分块 Prefill 的意义：把长 prompt 拆成 chunk，使“算一点、传一点”成为可能。传输与计算重叠后， 长上下文的尾部等待被摊薄；代价是调度更复杂、需要处理层序与 buffer 复用。
RISK 二次负载检查：Conductor 预选 D 节点后，本地调度器还会再查一次负载。若此时负载升高而拒绝请求， P 侧已经花掉的 Prefill 算力就浪费了——这是“全局预选 + 局部复核”架构的固有代价。
04COMPONENT / TRANSFER ENGINE

Transfer Engine：把“段”连成一张可远程读写的网

核心只有两件事：Segment 定义一个逻辑连续、可被远程读写的地址空间；BatchTransfer 把一组非连续区间从一个段搬到另一个段。在此之上，再叠加多网卡拓扑感知、端点连接管理与按协议的传输后端。

ABSTRACTION / SEGMENT

Segment：一段可被远程寻址的内存

既可以是 DRAM / HBM 提供的非持久 RAM 段，也可以是 NVMeoF 提供的持久段。每个客户端对应一个 TransferEngine，除一个 RAM Segment 外，还集成跨多线程、多网卡的高速传输管理。

RAM SegmentNVMeoF Segment注册即暴露
ABSTRACTION / BATCHTRANSFER

BatchTransfer：段间批量搬运

封装一组请求（数组形式，指定 READ / WRITE），在一个段内的一组非连续空间与另一段内对应空间之间同步数据，支持双向读写。定位类似异步、更灵活的 AllScatter / AllGather。

落到昇腾：七种传输场景对应七条物理链路

传输场景使用传输方式具体实现路径与说明
本地 Segment 之间AscendDirectTransport源与目标在同一进程内，由 Ascend Direct Transport 处理。基于 CANN 的 ADXL，通过 HCCS 或共享内存完成节点内 D2D / H2D / D2H 拷贝，无需经过网络。
本地 CPU ↔ 远端 CPUAscendRdmaTransport远端 Segment 注册为原生 RDMA 协议时进行协议桥接。数据路径：本地 CPU 内存 → RDMA WRITE → 远端存储（读取时反向）。
本地 HBM/CPU ↔ 远端 CPUAscendRdmaTransport最典型的跨节点场景。HBM 不能被标准 RDMA 网卡直接寻址，经 CPU bounce buffer 中转：WRITE 为 NPU HBM → D2H（aclrtMemcpyAsync）→ bounce buffer → RDMA WRITE → 远端；READ 为远端 → RDMA READ → bounce buffer → H2D → NPU HBM。
HBM ↔ HBM（节点内）AscendDirectTransport由 Ascend Direct Transport 通过 HCCS（华为缓存一致性系统）执行 D2D 拷贝，是延迟最低的路径。
HBM ↔ HBM（跨节点）ADXL + RDMA首选 Ascend Direct Transport 配合 RDMA，由 HIXL 等通信库在 NPU 间直接建立通道；条件不满足则回退到经 bounce buffer 的 AscendRdmaTransport。
HBM ↔ CPU 内存（节点内）AscendDirectTransport通过 CANN 的 aclrtMemcpyAsync 完成 H2D / D2H 拷贝，走 PCIe 总线。
本地 / 远端 NVMeoFNVMeoFTransport目标 Segment 为 File 类型时，利用 GPUDirect Storage（GDS）经 PCIe 直接从 NVMe 传到 DRAM / VRAM，绕过 CPU 实现零拷贝。vLLM-Ascend 公开文档的支持情况尚不明确。

05COMPONENT / MOONCAKE STORE

Mooncake Store：分布式 KV Cache 的“账本 + 仓库”

Master Service 以独立进程运行、对外暴露 RPC，负责整个集群逻辑存储空间的编排：节点加入退出、对象空间分配、元数据维护。Client 被上层应用调用，发起 Put / Get；同时它也可以托管一段连续内存成为存储服务器。global_segment_size = 0 时退化为纯客户端。

MASTER SERVICE

全局账本

编排逻辑存储空间池、管理节点加入/退出、对象空间分配与元数据维护。以独立进程运行，对外暴露 RPC 服务。可多活高可用，也可配合 etcd / Redis 做服务发现。

既是调用方，也是存储节点

06COMPONENT / CONDUCTOR

Conductor：回答“这个前缀，去哪个实例最划算”

Mooncake-Conductor 订阅来自推理引擎或存储后端的 KV 缓存事件，做标准化处理，维护一张全局前缀缓存表，并提供 HTTP API 用于动态服务注册与缓存命中查询。它要回答的问题只有一个：对该请求前缀，哪个已注册实例具有最佳的可用 KV 缓存局部性，且该前缀在哪些缓存层级上可用。

组件职责
EventManager管理 Conductor 生命周期、HTTP 服务器、动态注册、活跃服务映射，以及租户到实例的映射
ZMQClient连接发布者端点，消费事件帧，解码事件批次，跟踪序列号，并在重新连接后请求重放
KVEventHandler将解码后的引擎事件适配为 Conductor 的存储 / 删除事件，并丰富注册元数据
PrefixCacheTable维护特定模型上下文的前缀映射、引擎哈希到 Conductor 哈希的映射、介质元数据、DP-rank 元数据，以及查询时的命中计算

亲和调度：让第二次相同前缀请求回到同一张卡

部署口径 并非所有 PD 分离部署都必须上 Conductor 二进制：vLLM-Ascend 中也常用 load_balance_proxy_server_example.py 这类负载均衡代理做前置路由。 两者的区别是：Conductor 有全局前缀表与缓存位置感知，普通代理只看负载。
07INTEGRATION / VLLM-ASCEND

Mooncake 如何插进 vLLM-Ascend：三条链路，一个工厂

Mooncake 通过 KV config 注册到 vLLM；调度器依据注册的 connector 找到不同后端；KVTransferConfig 是入口，scheduler 负责调度，worker 负责真正执行。在 vLLM-Ascend 中，这一套被拆成 PD 点对点、KV Pool 存储、Offload 三条彼此独立的链路。

01注册

Mooncake 通过 kv config 注册到 vLLM，工厂记录 connector 模板。

02入口

KVTransferConfig 描述 kv_role、connector、端口与 extra_config。

03选择

Scheduler 依据注册的 kvcache connector 找对应后端。

04调度

Scheduler 侧做前缀命中判定、block 分配与请求编排。

05执行

Worker 侧注册 buffer、发起传输、落地 KV 并上线模型前向。

09ATTENTION COVERAGE

13TAKEAWAYS

三句话记住三套方案，一条链路由四种资源组成

Mooncake 的价值不在“更大的缓存”，而在于把 KV Cache 从实例附属状态提升为可独立扩展、调度和复用的集群资源。选型时先问规模与延迟哪个是硬约束，再问生态与可控性。

Memcache快 · 简 · 昇腾

GVA 直访、设备直发、免 key 解析；一个控制面 + 每节点常驻代理，部署最轻。

赢在极致延迟与轻量，受限于固定 8TB 段（A2 128 机 / A3 8 机）与闭源传输核。

单集群、要极致延迟 → 选它
Mooncake大 · 广 · 中立

完整 PD 解耦 + Store + TE + Conductor；多厂商、SGLang 原生、开源可改可再发布。

赢在规模化、生态与论文背书；代价是组件多、部署重、连接资源随节点数增长。

跨集群 / 多厂商 / 规模化 → 选它
元戎 datasystem全 · 活 · 标准

HBM 入池作传输/合并缓冲，DRAM/SSD 驻留对象；三档持久化、读序可配、加节点线性扩容。

赢在分层完备与水平扩展；依赖 openYuanrong / etcd 生态，昇腾为主。

昇腾原生 + 分层缓存 → 选它
VISION 组合而非二选一

“Memcache 近端 + Mooncake / 元戎远端”：近端用 GVA 直访吃极致延迟， 远端用分布式池化承接容量与跨集群复用。

现实约束：vLLM-Ascend 当前受单 backend 挂载限制，同实例无法挂多池；跨实例路由编排尚未就绪。组合是方向，不是现成开关。

如果只记五件事

01 · WHY

KV Cache 是新的“内存层级”

相同前缀反复计算是纯浪费。把前缀 KV 持久化成可共享资源，用存储换计算，是 TTFT 与承载能力的直接杠杆。

02 · HOW

三段链路缺一不可

块级哈希定位可复用前缀 → 增量 Prefill 只算新部分 → 传输与计算重叠搬到 D 侧。任何一段退化，收益都会打回原形。

03 · WHERE

昇腾上传输不是“一条路”

HCCS / PCIe / RoCE / bounce buffer / GDS 各有边界。HBM 不能被标准 RDMA 直接寻址，是理解所有昇腾传输问题的起点。

04 · FAILURE

故障大多来自“维度没对齐”

互联方式、并行切分（TP/DP/PP/CP）、KV spec（组数 / scale / metadata 槽）——三类问题的共同点是：某一条链路的两端对同一件事的理解不一致。

05 · ECOSYSTEM “采用 Mooncake”必须落到层：只用 TE、用 Store 建池、还是完整架构，是三件不同的事。 国内八家厂商里，真正以 Mooncake 为中心组织架构的只有月之暗面；京东、腾讯、阿里云是“自研主栈 + 组件”； 其余各有主栈，不能按行业惯例补写。
