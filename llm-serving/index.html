01

为什么 LLM Serving 比传统 DL 推理难

⤴ 返回架构图📄 原文

全局视角 ｜ 系列开篇立论：难在执行模型改变，而非模型变大

核心流程 · LLM 请求生命周期 vs 传统 DL

传统 DL：请求进入 → 组 Batch → 一次 Forward → 返回结果
LLM：请求进入 → Prefill（N 个 Prompt Token 并行、批量写 KV Cache）→ 首 Token → Decode Step（每步 1 个新 Token、追加 1 个 KV 位置、读全部历史 KV）→ 循环 → EOS / 长度上限

重难点

  1. 范式转移——服务对象从"一次 Forward"变成带动态生命周期与持久状态的生成任务：输入长度（几十到数万 token）、输出何时 EOS、每轮活跃请求集合均不可预知，传统"shape 固定 / 一次完成 / 内存一次分配"假设全部失效。
  2. Prefill vs Decode 双 Workload——Prefill 单步算 N 个 Token，Compute-Bound（瓶颈算力）；Decode 每步只算 1 个 Token 却要读全部历史 KV，Memory-Bound（瓶颈 HBM 带宽与 KV Cache）。适合一者的优化未必适合另一者。
  3. 吞吐-时延权衡——增大 Batch 共享权重读取、吞吐先升后饱和，但 TTFT / ITL / P99 恶化；目标是 SLO 约束下选执行规模，不是追求最大 Batch。
  4. 带状态推理——KV Cache 的位置、容量、复用与回收直接决定最大并发数、可支持上下文长度与整体吞吐，这是与传统 Serving 的本质区别。
  5. 贯穿全系列的 KV 账——Llama-3-70B（FP16、80 层、GQA-8、8×H100 TP=8）：每 token 每层 KV = 4KB、全模型 320KB/token；示例请求（2050 进 / 2350 出）KV 峰值约 734MB；每卡权重 17.6GB。

关键结论

① 三个根本变化：静态→动态执行、无状态→带状态、单一→Prefill/Decode 混合 Workload。

② 优化必须对症：提高 GPU 利用率不一定降低 Decode 延迟；只优化 Kernel 不解决排队；只优化 KV Cache 不改善长 Prompt 的 TTFT。

02

如何衡量一个 LLM Serving 系统

⤴ 返回架构图📄 原文

全局视角 ｜ 建立延迟 / 吞吐 / 效率 / 质量四维指标体系，并映射到瓶颈与优化方向

核心流程 · 指标分析流程

确认指标口径 → 区分 Prefill / Decode / 排队 / 网络因素 → 对比均值与 P95 / P99 → 结合 GPU、显存、带宽、通信定位瓶颈 → 选择与指标对应的优化方向 → 用 Goodput 与 SLO 达标率验证有效性

重难点

  1. TTFT ≠ Prefill 时间——TTFT = 排队 + 调度等待 + Prefill + 首 Token 生成 + 网络传输；TTFT 高不一定是 Kernel 低效，高并发时排队可能是主要部分。
  2. TPOT vs ITL——TPOT 是 Decode 平均每 Token 时间，用户感知的是逐 Token 到达间隔（ITL）；调度抖动可使平均 TPOT 正常而 ITL 的 P99 很差，流式体验必须看分位数。
  3. GPU 利用率的误导性——利用率高可能只是在等访存或通信；Decode 受带宽限制时 MFU 低也不代表低效，需结合 HBM 带宽利用率、通信时间综合判断。
  4. Goodput 才接近真实价值——单位时间满足 SLO 的有效请求 / Token 数；"吞吐高但 Goodput 低" = 拿延迟换吞吐，解法是 SLO-aware 调度、限 Batch 上限、资源隔离。
  5. 显存不是越满越好——过度填充导致新请求无法接入、抢占频繁、换入换出、P99 升高与 OOM 风险；须与命中率、抢占率联合分析。
  6. Requests/s 不可单独比较——脱离输入输出长度分布无意义；规范报告应含并发数、Token 数、TTFT、TPOT/ITL、P99。

相关知识

TTFTTPOTITLE2E LatencyQueueing TimeOutput/Total Tokens/sGoodputMFUP50/P95/P99SLO 达标率Cost per Token

关键结论

① 核心原则：不同指标对应不同瓶颈，不同瓶颈对应不同优化手段——不能用提高吞吐的方法解决 TTFT。

② 吞吐衡量做了多少工作，延迟衡量用户等了多久，Goodput 衡量满足 SLO 前提下完成了多少有效工作；在线服务应报告 均值 + P95/P99 + SLO 达标率。

03

鸟瞰 vLLM：一个请求如何穿过整个推理系统

⤴ 返回架构图📄 原文

全局视角 ｜ 自顶向下拆解 vLLM V1 控制面 / 数据面架构与请求完整数据通路，是全系列的代码地图

核心流程 · 一次请求的完整生命周期

Client → API Server（FastAPI，OpenAI 兼容）→ AsyncLLM 分词 → EngineCore.step() → Scheduler.schedule() → SchedulerOutput → Executor → Worker → ModelRunner.prepare_inputs → GPU Forward → Sampling → Detokenizer → SSE 流式返回

重难点

  1. 控制面 / 数据面分离——Client→EngineCore 是入队路径（传"生成什么"），EngineCore→Worker→ModelRunner 是执行路径（带本轮 batch 与 block 布局）；调度状态留在 EngineCore，模型侧只负责单次前向。
  2. EngineCore 中央调度大脑——step() 驱动整个推理循环；初始化顺序：model_executor → KV Cache → Scheduler。
  3. 资源管理双核——Scheduler（约 3000 行）决定每轮谁参与推理、分配多少 token 预算；KVCacheManager 负责 KV 物理块的分配、释放、复用与驱逐。
  4. Executor 抽象与 Ray 的真实定位——"用不用 Ray"是部署方式差异而非执行模型差异；"一个 GPU 固定绑一个 Worker 进程"不是绝对规则。
  5. 数据流的形态变化——文本 → token_ids → 调度决策（block_table）→ 张量输入（positions/slot_mapping）→ logits → token id → 文本，同一请求在各层以不同形态流转。

相关知识

API ServerAsyncLLMEngineCoreRequestSchedulerOutputblock_table / slot_mappingKVCacheManagerExecutor（UniProc/Multiproc/Ray）WorkerModelRunnerSampling（top-p/top-k/temp）DetokenizerSSE

关键结论

① 模块分工一句话：EngineCore 驱动循环，Scheduler 决定这轮谁跑、跑多少 token，Executor 把任务分发下去，ModelRunner 真正调用 GPU 算。

② 与 01 篇"四问"对齐构成系列骨架：这轮谁执行多少→Scheduler；状态放哪→KVCacheManager；怎么算得更快→ModelRunner/Backend；怎么扩出去→Executor/集合通信。

04

Scheduler：GPU 这一轮到底给谁用

⤴ 返回架构图📄 原文

核心流水线 · STEP ② ｜ GPU 每轮迭代把计算额度分给哪些请求、各推进多少 token（对应 vLLM v1/core/sched/scheduler.py）

核心流程 · schedule() 一轮

确定 Token Budget（如 512）→ 遍历 Running：算 remaining → num_new_tokens = min(剩余， 预算， 长Prefill阈值) → allocate_slots 分 KV 块 → 失败则抢占 → 遍历 Waiting：算前缀命中并准入 → 输出 SchedulerOutput → ModelRunner 执行 → 更新进度进下一轮

重难点

  1. Continuous Batching——Static Batch 须等最慢请求、GPU 利用率随完成逐渐下降；Continuous Batching 每轮迭代前重新决定本轮服务谁，完成即释放、新请求每轮可尝试加入。
  2. Chunked Prefill 的 TTFT↔TPOT 权衡——32K 长 Prompt 一次 Prefill 造成队头阻塞（所有 Decode 请求 TPOT 尖峰）；拆 Chunk 后 TTFT 上升换 TPOT 平稳（例：2050 token、阈值 512 → 512×4+2）。
  3. Token Budget 资源分配模型——Request 是调度对象、token 是资源：约束 Σx_i ≤ Budget 且 0 ≤ x_i ≤ remaining_i；例 A 400 + B 1 + C 1 = 402，剩余 110 还可当场接纳 Waiting 的 D。
  4. Mixed Batch 统一抽象——Prefill（remaining 大）、Decode（remaining≈1）、Speculative（remaining>1）只是推进需求取值不同，无需独立 Scheduler，一轮可混排（如 512 = Prefill 256 + Decode 1 + Spec 5 + Prefill 250）。
  5. 双重资源约束——Token Budget 管"本轮最多算多少"，KV Cache 管"装不装得下"；预算够但 Free Blocks 不足照样无法接纳（Admission Control）。
  6. Preemption 与防震荡——V1 主用 Recomputation（释放 KV、LIFO 插回 Waiting 队首），因 Prefix Cache 命中使重算代价大降；Swapping 省算力但吃 CPU 内存与 PCIe 带宽；Watermark 预留安全余量防 Admission→Preemption 反复震荡。

关键结论

① Scheduler 本质不是维护"Batch"，而是 Token Budget 与 KV Cache 双重约束下，每轮动态决定谁执行、各推进多少 token。

② Prefill 与 Decode 不是两套调度算法，只是 token 推进需求不同；上层优化（如投机解码）只改变一轮推进的 token 数，不改变调度抽象。

05

KV Cache：LLM Serving 的第一号内存问题

⤴ 返回架构图📄 原文

核心流水线 · STEP ③ ｜ KV 显存为何被浪费，PagedAttention 如何分页管理、复用与压缩瘦身

核心流程 · KV Cache 生命周期

逻辑序列按 block_size=16 切块（2050 token → 129 块）→ allocate_slots：BlockPool 从 LRU 空闲队列取块（不足则驱逐缓存块）→ Block Table 登记虚拟块→物理块映射 → Prefill 批量写 / Decode 每步增量追加 1 slot → Kernel 只认 Block Table 按块读 → 完成 free：ref_cnt 归零才回收 → 写满的块进 Prefix Cache 复用

重难点

  1. 碎片灾难源于"不确定性"——按最大长度预留连续显存产生内部 + 外部碎片；PagedAttention 论文（SOSP'23）实测当时 SOTA 系统有效 KV 仅占显存 20.4%~38.2%，约 60%~80% 被浪费。
  2. OS 分页思想搬到 GPU——逻辑块→物理块经 Block Table 映射（类比页表），请求看连续序列、KV 实际零散存放；"写满当前块再要一块"使预留彻底消失。
  3. 只有写满的块才可缓存——Prefix Cache 命中粒度对齐 block_size；2000 token system prompt 恰 125 整块，第二请求全命中：TTFT 从约 92ms 降到 5ms 量级，625MB KV 靠 ref_cnt 共享而非复制。
  4. 链式哈希的正确性——块哈希 = f(前驱块哈希， 本块 token ids, extra_keys)，只有完全相同前缀才命中；NONE_HASH 随机（防跨租户探测）vs 设 PYTHONHASHSEED 可复现是一对取舍。
  5. 三层压缩正交可叠加——管理层（PagedAttention / Prefix Cache）× 架构层（GQA / MLA：Llama-3-70B GQA-8 KV 为 MHA 的 12.5%，MLA 存 576 维 latent 约 3~4×）× 数值层（FP8 省 50%）。
  6. 量化与分层存储——KV 是"并发×上下文"乘积（70B 单请求 4K 上下文 FP16 达 1.34GB）；FP8 实践中最安全（softmax 指数会放大 Key 误差）；不足时重算 / 换出 / 量化+Offload 三选一。

关键结论

① 显存不是被模型吃掉的，是被"不确定性"浪费掉的——预留式分配下有效 KV 仅占两到四成。

② Prefix Cache 是性价比最高的优化之一；抢占重算因 Prefix 命中而远比理论便宜；三层优化（管理×架构×数值）正交可叠加。

06

GPU 执行：如何让每个 Token 算得更快

⤴ 返回架构图📄 原文

核心流水线 · STEP ④⑤ ｜ 已确定要算的 token 如何算得更快——Decode 侧四种浪费形态及对策

核心流程 · Decode 一步 ~10ms 的四种浪费与对策

GPU 等 CPU 发指令 → CUDA Graph 录制重放 ｜ GPU 等 HBM 送数 → FlashAttention / 算子融合 ｜ 每个字节太胖 → FP8/INT8 量化 ｜ 轮次太多 → 投机解码（Draft 猜 K 个 → Target 一次并行验证 → 拒绝采样 → KV 回滚重采样）

重难点

  1. Launch-Bound 气泡——单 kernel 执行时间 < CPU 提交时间（2~5μs）时队列抽干出气泡；Decode 小 kernel 下 400 个 kernel 一步仅 37.5% 时间在干活，故 CUDA Graph 基本只对 Decode 有意义。
  2. CUDA Graph 模式选择——约束：kernel 形状固定（按 Batch Size 分桶预捕获）、内存地址固定、不支持动态控制流；工业主流 FULL_DECODE_ONLY，PD 分离后 Decode 节点 FULL、Prefill 节点 PIECEWISE。
  3. FlashAttention 收益边界——显存 O(N²)→O(N) 无条件成立，但 FLOPs 一分未减，是带宽 + 显存胜利而非计算胜利；Decode 侧 query_len=1 切不动 query 方向，须改 split-KV / Flash-Decoding 沿 KV 维切。
  4. 量化对象不均匀受益——权重量化直击 Decode 带宽（权重读取减半），激活量化主要加速 Prefill GEMM，KV 量化换并发与上下文；优化前必须先判断瓶颈在哪侧。
  5. 投机解码本质与边界——不消除自回归依赖，被并行化的是"验证"不是"生成"；拒绝采样保证输出分布与 Target 严格一致；接受率一低收益即蒸发，高并发高利用率下额外 Draft 计算可能负收益。

关键结论

① 3% vs 97%：示例中 Prefill ≈92ms（3%），Decode 300 步 ≈3000ms（97%）——端到端优化必须主攻 Decode；权重读取下界约 5.3ms/步，实测 ~10ms。

② CUDA Graph 上限省 20%、实测 5~15%；投机解码示例等效 TPOT 15ms→7.7ms（约 2×），本质是"拿闲置算力换延迟"；量化质量必须用 benchmark 实测。

扩展维度 · 横向 ｜ DP / TP / PP / EP / CP 各切什么、通信代价多大、如何组合选型

核心流程 · 选型决策链 与 TP 单层执行

装不下一个 Linear → TP（层内切矩阵）｜ 整模型太大 → PP（按层切流水）｜ Expert 太多 → EP（按 Expert 切）｜ 上下文太长 → CP（按序列切）｜ 要更多吞吐 → DP（整体复制，永远最外层）
TP 单层：X → QKV Column Parallel（无通信）→ Attention 本地 → O Row Parallel → All-Reduce → Gate/Up Column → Down Row → All-Reduce（每层 2 次）

重难点

  1. TP 的 Column/Row 配对——Column 的输出分片恰为 Row 的输入分片，层内中段零通信、段末 All-Reduce 在关键路径同步等待；Decode 一步逻辑通信量 ≈80MiB，故 TP 只适合 NVLink 机内互联、跨机评分最低。
  2. PP 流水线气泡——Fill / Drain 阶段部分 GPU 无活可干；训练可用海量 microbatch 填满，在线推理请求动态变化，气泡与负载不均难彻底消除——PP 适合重吞吐场景，单请求低延迟需谨慎。
  3. PP 重构 KV Cache——KV 按层切片散落各 stage（单卡只存 1/PP 的层）；但引入跨 stage 全局调度一致性难题：各 stage 须同步分配/释放同一请求的块。
  4. EP 的负载均衡——瓶颈是 Router + 动态 Dispatch + 变长 Grouped GEMM；同步模式下整层时间 = max(各卡时间)，一个热门 Expert（96 token vs 均值 32）即可拖垮整层；Capacity Factor 大则开销大、小则丢 token。
  5. 通信计算重叠——token 分 Chunk 错相执行（算 Chunk0 时为 Chunk1 Dispatch），总耗时从三者之和降到 ≈max(T_comm, T_compute)；Expert 计算太小时通信藏不住。

相关知识

关键结论

① DP 与其余四者不同类：TP/PP/EP/CP 解决"装不下"（被迫拆分），DP 解决"想要更多"；生产部署 = 先用 TP/PP/EP/CP 塞进一组卡，再用 DP 复制 N 份。

② 经验法则：TP 优先 NVLink 机内；PP 用于跨机；EP 通常 TP×EP=总卡数；>8 卡 → TP=8 + PP=N；EP 性能 ≈ 通信效率 × 负载均衡 × 本地 GEMM × 重叠能力。

扩展维度 · 横向 ｜ 推理系统的性能深水区——通信如何拖慢推理、如何被隐藏与压缩

核心流程 · 问题定位链 与 优化优先级链

nvidia-smi topo -m 确认拓扑 → NCCL_DEBUG 确认识别结果 → NCCL Tests 基准（区分库/应用问题）→ 按消息规模分方向（小消息查延迟、大消息查带宽）→ 减少同步/拷贝/次数 → 计算通信重叠 → CustomAllreduce → 最后才调 NCCL_ALGO/PROTO

重难点

  1. Decode 阶段通信敏感——单步生成 Token 少、GEMM 计算量下降，但跨 GPU 同步仍在；通信启动延迟、同步等待、小消息处理效率成为主导瓶颈。
  2. 带宽口径不可直接比——NVLink 宣传值可能是单卡聚合 / 双向 / 系统总量；量级参考：NVLink 数百 GB/s、PCIe Gen5 x16 约 64GB/s 单向、IB NDR 400Gb/s 约 50GB/s。
  3. 多开 Stream ≠ 自动重叠——争用同一硬件资源、隐式同步、输入未就绪都会让两 Stream 退化串行；关键是重新设计依赖关系，而非简单加 Stream。
  4. All-Reduce 拆解的收益来源——All-Reduce = Reduce-Scatter + All-Gather，拆分后总通信量同量级，收益来自重叠（局部就绪即算）而非减少字节；需后续计算能按分片执行。
  5. CustomAllreduce 适用边界——单机多卡 + 良好 P2P/NVLink + 小消息 + Decode 低延迟敏感时优于 NCCL；跨节点 / 大消息仍归 NCCL。

相关知识

NCCL通信原语（All-Reduce/All-Gather/Reduce-Scatter/All-to-All）Ring / Tree 算法小消息 vs 大消息协议GroupCoordinatorGPUDirect RDMANUMA 亲和性MoE 通信链

关键结论

① 端到端时间 = 计算时间 + 无法隐藏的通信时间 + 同步等待 + 数据重排拷贝；目标是降低通信在完整推理路径的可见时间，而非某次 All-Reduce 基准数字最大。

② 无重叠时 ≈ T_compute + T_comm，重叠后 ≈ max(两者)；调优铁律："先确认拓扑，再定位瓶颈，最后修改参数"。

扩展维度 · 纵向 ｜ vLLM 如何用分层抽象在不污染运行时的前提下快速接入新模型

核心流程 · 抽象主链路 与 适配机制演进

ModelConfig（配置语义）→ ModelRegistry（模型发现）→ nn.Module + Protocol（能力契约）→ ModelLoader / WeightsMapper（权重装配）→ Worker + ModelRunner（运行时执行）→ Attention Metadata → Attention Backend → Kernel
机制演进：硬编码 → Monkey Patch → Custom Op → IR → 组合标准计算原语

重难点

  1. 每种差异都会捅穿多层——换 Attention 变体影响 Kernel 和 KV 布局；Mamba 的 state 不是块状；引入 MoE 影响路由 / Dispatch / 通信 / 负载均衡——而新架构发布频率是周级。
  2. 四目标互相冲突——正确性、性能、可维护性、可扩展性不总一致；专用 Kernel 性能高但灵活性低，适配本质是工程折中。
  3. 动态运行时 vs 静态执行图——batch/序列长度持续变化、KV 地址不固定，编译器却要稳定 shape；解法是"动态性上浮（Scheduler/Metadata）、静态性下沉（torch.compile / CUDA Graph / shape bucketing）"。
  4. 权重装配最易出错——同时含重命名、拆分合并（QKV / gate-up）、并行切分、量化格式、设备布局；加载错误不一定崩溃，可能只是 logits 偏差，需参数→Shape→统计量→单层输出→logits 逐级验证。
  5. MLA 改变缓存语义、MTP 引入事务化状态——KV Cache 从 [b,s,h,d] 变 latent_cache，波及分配 / 写入 / 前缀复用；投机回滚是涉及序列、block table、位置、采样状态的一致性事务。

① 核心工程哲学："动态性上浮、静态性下沉、以契约连接两者"。

② DeepSeek 接入本质是三次协议扩展：MLA 扩展缓存协议、MoE 扩展执行协议、MTP 扩展状态协议；Attention 并不总是第一瓶颈——先 profiling 证明关键路径，再选择性特化。

硬件解耦：如何不让芯片差异污染 Serving 核心

扩展维度 · 底座 ｜ 同一套 Serving 逻辑跨芯片运行且核心不被硬件分支污染（以昇腾 OOT 适配为例）

核心流程 · Platform 诞生链 与 能力派发

读取运行环境 → 检测可用设备 → 加载内置平台或 OOT 插件 → 选择匹配的平台实现 → 暴露全局 current_platform → 后续代码统一查能力
能力派发：current_platform ─ Attention Backend Selector（动态选择）／ Kernel Import（直接导入）／ Device Communicator（NCCL/RCCL/HCCL）／ Worker / Device Runtime ／ 平台配置

重难点

  1. if-else 反例的代价——在 Scheduler / KV Cache / 执行器里堆 is_cuda() / is_ascend() 分支：每加一种芯片要改多个核心模块，测试矩阵从"功能 × 模型"膨胀为"功能 × 模型 × 芯片"。
  2. "三层调用栈"是误解——真实关系不是 Platform→Backend→所有 Kernel 的调用链；大量 Kernel、通信组件由 Platform 直接提供，Attention Backend 只是"其中一个重要的动态选择器"。
  3. Attention 为何单独做 Selector——计算量大 + 硬件敏感 + 场景复杂（prefill/decode、paged KV、MLA、head size、dtype）；同一块 GPU 上不同配置可能选中 FlashAttention、FlashInfer 或 Triton。
  4. Attention Backend ≠ 一个数学算子——必须理解 vLLM 运行时语义：Attention Metadata、Block Table / KV 布局、prefill/decode 分派；只会算 attention 但不懂 block 布局的算子当不了完整 Backend。
  5. KV Cache 分层纪律与 OOT 边界——Manager 只管逻辑 block 且平台无关，平台 Worker 只管物理落地；"主仓库一行不改"依赖主仓库已有稳定扩展点，抽象缺失时插件仍需提补丁。

关键结论

① 三句话：Serving 核心依赖抽象能力而非具体芯片；Platform 是硬件能力中心但不是所有组件的唯一调用父类；OOT 独立演进的前提是主仓库提供稳定扩展契约。

② 验收标准：能在 NPU 上返回结果只说明链路打通；在真实模型、真实 batch、真实上下文长度下稳定达到目标吞吐，才算完成工程适配。

部署演进 ｜ 为何及如何把 Prefill / Decode 拆成两个资源池，并用 KV Transfer 衔接

核心流程 · 一次请求的 5 步旅程

① Router 选 Prefill 节点（按 Prompt 长度 / 队列 / Prefix 命中）→ ② P 节点前向计算 Prompt、生成各层 K/V → ③ KV Transfer（KV Tensor + block table + 元数据）→ ④ D 节点接收写入、重建映射（不重复 Prefill）→ ⑤ 持续 Decode 直至完成

重难点

  1. 两种资源画像冲突——Prefill 计算密集、优化 TTFT；Decode 访存敏感、优化 TPOT。混部的问题不是"不能同时跑"，而是需求不同却共享调度与硬件：长 Prompt 抢占 Decode、Decode 占 KV 限制 Prefill batch。
  2. KV Transfer 是真正难点——KV bytes/token = 层数 × 2 × KV_heads × head_dim × 字节数；示例 320KB/token × 2050 ≈ 641MiB，50GB/s 下限仅 12.8ms，但真实交接 = KV 生成 + 元数据 + 传输 + 写入 + 状态确认 + Decode 启动六段之和。
  3. 传输与计算重叠（按层流水）——理想是 Layer 0 KV 到达即开算；能否成立取决于 Connector / Worker / Backend / Cache 布局协作，任一环不支持则退化为全量传输后串行。
  4. KV Affinity 路由——同前缀请求黏同一 Decode 节点复用 Prefix Cache，但过度会造热点；路由代价 = 排队 + 传输 + 容量压力 − Prefix 命中收益。
  5. 故障恢复三策略——重算（简单但长 Prompt 贵）/ 远端 KV 恢复（免重算但引入存储与版本问题）/ 复制（快但费带宽显存）；KV 是可重建状态，不追求数据库式强一致。
  6. PD 分离非无条件划算——判据：KV 传输时间 + 协调时间 < 混部排队与调度干扰。

相关知识

KV Connector（控制面/数据面）三层职责：语义/索引/传输NIXLLMCacheMooncakePrefix Cache 复用分层 KV Cache独立扩缩容

关键结论

① 真正难点不在"分两个池"，而在 KV Cache 的跨节点传输、查询、复用与恢复。

② KV Cache 从本地状态变成分布式状态后，Serving 从单机调度问题演进为集群状态管理问题——从"本地执行系统"走向"分布式状态系统"的关键一步。

部署演进 · 第 10 章图解深化 ｜ P→D 到底传什么（7 项内容）、异构部署的 7 项关键约束

核心流程 · P→D 一次完整交接

P 侧：Router 决策 → Prompt Forward 生成各层 K/V → 按 block 写入（布局 / dtype）→ 链式哈希进 Prefix Cache → 备齐 7 项元数据 → 通道：KV Transfer（理想走 GPUDirect RDMA 直达，支持则按层流水）→ D 侧：分配 + 布局/dtype 转换 → 写入重建 block table → 状态确认 → 接管 Decode

重难点 · 异构部署 7 项约束（①②⑤ 需两侧同时满足）

  1. ① 布局与分页参数兼容（最核心）——D 侧 Kernel 只认 block table，block_size 不一致则整张映射失效；641MiB 传过去也读不对。
  2. ② dtype 与量化格式互认——同一量化名称在不同平台实现不同（scale 布局平台相关）；FP16↔FP8 在线转换多一趟读写；softmax 对 Key 误差指数敏感。
  3. ③ 传输路径不劣化——一侧不支持 GPUDirect RDMA 就经 Host 中转 +2 次拷贝；带宽 50→25GB/s 时下限 12.8→25.6ms，直接吃掉 PD 分离省下的 TTFT。
  4. ④ 按层流水能否成立——start_load_kv / wait_for_layer_load 接口需两侧平台都支持分层等待，任一侧不支持即断流退化串行。
  5. ⑤ Prefix Cache 跨节点复用前提——哈希可复现（显式 PYTHONHASHSEED）+ extra_keys 一致 + 模型版本 / dtype / 布局复用边界成立，否则"少传"落空甚至错误复用。
  6. ⑥ 接收端内存分配与同步语义——异构设备异步执行、错误可能延迟到同步点才暴露；须"写入-确认-开算"事务化防脏读。
  7. ⑦ 调度配比与故障恢复的全局约束——P/D 配比、恢复策略需全局视角统筹，属于集群级而非单节点问题。

关键结论

① 量级结论：320KB/token × 2050 token ≈ 641MiB；50GB/s 下 12.8ms 只是带宽下限，真实交接是六段链路之和。

② 对比口诀：同构 PD 难点是"传得快"；异构 PD 难点是"对方认得"（布局 / dtype / 哈希 / 流水语义兼容）+ "路径不劣化"；解法 = Platform 能力查询 + 启动期校验提前失败。

部署演进 · 前瞻 ｜ Serving Infra 从"模型执行器"到"分布式智能操作系统"的演进方向

核心流程 · 智能任务的生命周期 与 编译边界扩大

带状态智能任务：接收请求 → Prefill → 生成部分结果 → 调用外部工具 → 等待返回 → 恢复上下文 → 继续生成
编译边界：Kernel Compiler → Graph Compiler → Model Compiler → Serving Plan Compiler
未来分层：模型与编译层 → Serving Runtime → Inference State Plane → 分布式调度编排 → 硬件 / 数据中心

重难点

  1. 性能指标重新定义（Goodput）——tokens/s 高但大量超时或 GPU 消耗过多不算高效；目标是在满足 SLO 前提下以更低成本完成更多有效任务。
  2. Serving Plan Compiler——输入模型结构 / 硬件拓扑 / SLO / 负载预测，输出算子、融合、布局、并行、Batch、Cache、通信、调度参数的完整执行计划；一个模型拥有多套计划，Runtime 按负载选择。
  3. 自动化并行是联合优化——P* = argmin(C_compute + C_memory + C_communication) 且满足 TTFT/TPOT SLO；TP 降显存但增通信、PP 有气泡、DP 复制 Cache、EP 依赖 All-to-All、CP 增状态交换。
  4. 拓扑感知规划 vs PD 容量均衡——前者解决 Worker 内部如何切分（需理解 NVLink / PCIe / NUMA / 故障域），后者解决集群 P/D 各部署多少——两个不同层次。
  5. Inference State Plane（推理状态平面）——KV Cache、Prefix Cache、Session、工具结果等统一为一等资源，需寻址 / 迁移 / 复制 / 版本 / 失效 / 恢复等能力；"传输还是重算"成为运行时决策。
  6. Goodput 驱动调度与异构感知——max(Goodput − α·Cost − β·SLO Violation − γ·Energy)；按硬件特性放置请求：大显存→长上下文、高算力→Prefill、高带宽→Decode、高网络带宽→KV Transfer。

① 四个转变：手工配置→自动执行计划、本地缓存→分布式状态平面、单体推理→多阶段分布式执行、GPU 利用率→Goodput/SLO/成本联合优化。

② 核心问题从"如何在一张 GPU 上更快运行模型"变为"如何让计算、状态和调度协同，使智能系统持续、低成本、可恢复地完成任务"。
