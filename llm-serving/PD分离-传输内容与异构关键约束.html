PD 分离：P→D 传输什么 · 异构下的关键约束

PD 分离不是"Prefill 服务返回结果、Decode 服务重新开始执行"，而是 「Prefill 服务计算出中间状态，Decode 服务接管这个中间状态」——中间状态就是 KV Cache。 左图 P 节点产生状态，中间通道完成 KV Transfer，右图 D 节点接管状态。

同构部署默认两侧一致的东西，异构后全部要显式对齐：图中红色编号 ①–⑦ 标出关键约束的发生位置—— 同一编号出现在两侧，意味着该约束需要 P、D 两边同时满足。

📐 量级（贯穿全文例子，Llama-3-70B · 80 层 · GQA-8）： KV bytes/token = 层数 × 2(K,V) × KV_heads × head_dim × 字节数 = 320 KB → 2050 token prompt ≈ 641 MiB； 50 GB/s 下带宽下限 ≈ 12.8 ms，但真实交接 = KV 生成 + 元数据准备 + 网络传输 + 目标端写入 + KV 状态确认 + Decode 启动。

1 KV 布局与分页参数兼容最核心：传过去 block table 必须能被对面的 Kernel 解释

是什么：P 侧按自己的分页方式（block_size、head 排布、层组织）写 KV，D 侧 Attention Kernel 只认 block table； 两侧参数不一致，641 MiB 传过去了也读不对。

⚠️ 异构下为何关键

  • 跨节点传输时，「不同并行配置下布局是否兼容」是 KV 索引缓存层必须回答的问题。
  • block_size 必须一致——否则虚拟块→物理块的整张映射失效；KV head 排布、head_dim、层的组织方式也要互认。
  • MLA 模型尤其特殊：存的是 latent 而非完整 K/V；对压缩缓存，copy_blocks / cache swap / prefix caching 不能假设缓存具有传统 K/V 的形状和语义。
  • 两侧平台各自的 Attention Backend 对缓存布局有各自的假设。

2 dtype 与量化格式互认FP16↔FP8 在线转换，scale 布局平台相关

是什么：传输元数据里就有「数据类型和布局」。若 P 侧 FP16 KV、D 侧 FP8（或两侧量化粒度不同），必须在线反量化/重量化。

⚠️ 异构下为何关键

  • 「同一种量化名称，在不同硬件平台上可能对应不同实现」——scale 布局（per-token / per-head）、反量化位置都是平台相关的。
  • 转换本身有开销：反量化→重量化多一趟读写，直接加在交接延迟上。
  • 精度风险：需注意 softmax 对 Key 误差特别敏感（指数放大误差），两侧精度不一致会叠加误差。

3 传输路径与带宽不劣化GPUDirect RDMA 是否可用，决定 12.8 ms 还是 25.6 ms+

是什么：跨节点理想路径是 GPU→NIC→远端 GPU 的 GPUDirect RDMA；异构两侧若有一方不支持，就要经 Host Memory 中转、多两次拷贝。

⚠️ 异构下为何关键

  • 跨节点路径 GPU HBM→PCIe→NIC→IB/RoCE→…；GPUDirect RDMA 未启用时数据经 Host Memory 中转，额外拷贝与延迟。
  • 量级敏感：641 MiB 下有效带宽 50→25 GB/s，下限 12.8→25.6 ms——直接吃掉 PD 分离省下的 TTFT。
  • 真实链路还包括更多因素：KV 切分方式、元数据交换、PCIe/NVLink 路径、RDMA 协议开销、DMA 调度、多请求并发带宽竞争。

4 按层流水能否成立理想是 Layer 0 KV 到达就开算 Layer 0；任一侧不支持即退化为串行

是什么：传输与计算重叠是 PD 分离收益的关键；理想是「Layer 0 KV 到达就开始算 Layer 0」，能否按层流水取决于 KV Connector、Worker、Attention Backend、Cache 布局和底层传输实现之间的协作。

⚠️ 异构下为何关键

  • Worker 侧接口 start_load_kv / wait_for_layer_load / save_kv_layer ——两侧由不同平台提供，任何一侧不支持分层等待/保存，流水即断。
  • 退化为「整请求 KV 到齐再 Decode」→ 传输与计算完全串行，此时PD 分离的收益会显著下降。
  • layer 信息元数据、逐层确认机制都要两侧语义对齐。

5 Prefix Cache 跨节点复用前提哈希可复现 · extra_keys 一致 · 有效性边界成立，否则「少传」落空

是什么：跨节点不是每次全量搬运——前缀命中可复用远端已有 KV。但复用的正确性有一串前提，异构下每一项都可能不成立。

⚠️ 异构下为何关键

  • 链式哈希 = f(前驱块哈希, token_ids, extra_keys)；跨进程/跨节点对得上就必须放弃随机 NONE_HASH 默认，显式设 PYTHONHASHSEED（可复现性与不可预测性的取舍）。
  • extra_keys（LoRA、多模态、cache_salt）要求两侧收集口径一致，否则错误复用。
  • 复用边界包括：远端 KV 是否仍有效、不同模型版本能否复用、不同数据类型能否复用、不同并行配置布局是否兼容、被驱逐后如何通知。

6 接收端内存分配与同步语义确认「写完」才开算——异构设备的异步与错误暴露时机不同

是什么：「接收端内存分配、Tensor 布局转换、传输完成后的同步」是真实交接延迟的组成部分；做不严则是正确性问题。

⚠️ 异构下为何关键

  • 异构设备的内存池、分配器行为不同，需按设备单独适配。
  • 不同设备异步执行、算子错误可能延迟到同步点才暴露——同步语义适配是最容易被低估的部分。
  • 状态确认不严格 → KV 尚未写完就开始 Decode → 读到脏数据/缺数据，且这类错误难以复现排查。

7 调度配比与故障恢复全局约束：异构吞吐单独标定；KV 可重建 → 重算 vs 恢复的权衡

是什么：异构两侧吞吐特征不同，扩缩容与路由不能共用同一套标定；故障后 KV 是可重建状态，恢复策略要重新权衡。

⚠️ 异构下为何关键

  • P 池看输入 token 速率 / TTFT，D 池看活跃请求 / TPOT / KV 使用率——异构下要按各自硬件单独标定，否则配比失衡（一侧堵、一侧闲）。
  • KV Affinity 路由需计入两侧网络位置差异；路由代价 = Prefill 排队 + KV 传输 + Decode 排队 + 容量压力 − Prefix 命中收益。
  • 三种恢复策略：重算（简单，长 Prompt 贵）/ 远端 KV 恢复（免重 Prefill，引入存储成本）/ 复制（快但费带宽）——异构下「重算」常比维护跨硬件兼容的 KV 持久化更省事。
